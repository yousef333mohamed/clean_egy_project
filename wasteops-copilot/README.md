# WasteOps Decision Intelligence Copilot

This repository currently implements Step 2: the FastAPI and PostgreSQL/pgvector database foundation for WasteOps. It defines the exact operational dataset schema, asynchronous application sessions, Alembic-managed migrations, and application/database health endpoints.

CSV ingestion, document ingestion, embeddings, RAG, LLM calls, authentication, prediction models, and a frontend are intentionally not implemented yet. The CSV files under `data/raw` are unchanged reference inputs and are not loaded automatically.

## Current architecture

```text
FastAPI
  ├── GET /api/health
  └── GET /api/health/database
               │
       SQLAlchemy async engine
               │
       PostgreSQL 16 + pgvector

Alembic ── psycopg sync connection ── schema migrations
```

The model registry contains:

- Smart bins, readings, and daily operational records
- Trucks and daily trip logs
- Workers and daily attendance
- Region-level daily environmental records
- A future-facing document-chunk table with JSONB metadata and a pgvector column

Relationships are created only for actual identifiers (`bin_id`, `truck_id`, and `worker_id`). Region strings are indexed where useful but never treated as foreign keys.

## Requirements and installation

- Python 3.12
- Docker with Docker Compose, or PostgreSQL 16 with the pgvector extension

```bash
python -m venv .venv
python -m pip install -e ".[dev]"
cp .env.example .env
```

On PowerShell, activate with `.venv\Scripts\Activate.ps1` and copy configuration with `Copy-Item .env.example .env`.

The supplied URLs use the Compose hostname `database`. When running Alembic or Uvicorn directly on the host, override the host to `localhost`:

```env
DATABASE_URL=postgresql+asyncpg://wasteops:wasteops@localhost:5432/wasteops
DATABASE_SYNC_URL=postgresql+psycopg://wasteops:wasteops@localhost:5432/wasteops
```

Do not use the development password in production. Supply database credentials through a secret manager and use least-privilege roles.

## Database workflow

Start only the development database:

```bash
docker compose up -d database
```

Apply and inspect migrations:

```bash
alembic upgrade head
alembic current
alembic history
```

Generate a future migration after modifying SQLAlchemy models:

```bash
alembic revision --autogenerate -m "migration description"
```

Review every autogenerated migration before applying it. Alembic is the only schema-creation mechanism; application startup never calls `Base.metadata.create_all()`.

## Run the API

```bash
uvicorn app.main:app --reload
```

Expected liveness response from `GET /api/health`:

```json
{"status": "ok", "service": "WasteOps Decision Intelligence Copilot", "environment": "development"}
```

Expected readiness response from `GET /api/health/database` when PostgreSQL is available:

```json
{"status": "healthy", "database": "connected"}
```

Database failures return HTTP 503 with a safe message. Full exceptions are written to structured application logs without being returned to clients.

## Tests and linting

```bash
pytest
ruff check app tests migrations
```

Unit tests inspect PostgreSQL-specific SQLAlchemy metadata without using SQLite or a production database. The optional integration test verifies actual PostgreSQL check-constraint behavior against a separately configured migrated database:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://wasteops_test:test@localhost:5432/wasteops_test pytest -m integration
```

Tests marked `integration` are skipped when `TEST_DATABASE_URL` is absent.

## Data-model notes

- Telemetry timestamps use timezone-aware PostgreSQL timestamps.
- Coordinates and measurements use fixed-precision numeric columns.
- Composite unique constraints prevent duplicate historical observations.
- `service_completion_time_min` remains nullable because the source contains missing values.
- Inspection of all 10,170 attendance rows found `performance_score` values ranging from 0 through 100, supporting its database check constraint.
- The document vector dimension is read from `VECTOR_DIMENSIONS` by the model. The initial immutable migration creates 1,536-dimensional vectors; changing dimensions requires a new migration.
- Downgrading removes project tables in dependency order and deliberately preserves the shared `vector` extension.
